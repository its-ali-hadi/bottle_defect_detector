# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An AI-assisted quality-inspection tool: it watches a conveyor belt (camera or video file) for white bottles, crops one clear image per bottle, sends the crop to Anthropic Claude for defect analysis, and writes results to JSON + Excel (with Arabic-language defect labels/summaries). Ships as both a CLI (`bottle_detector`) and a PySide6 desktop GUI (`run_gui.py`), the latter packaged into a Windows EXE via PyInstaller.

## Commands

Setup:
```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt   # add requirements-gui.txt for the desktop GUI
```

Run the detector (CLI):
```bash
.venv/bin/python -m bottle_detector --source assets/test.mp4 --no-ai --no-display   # smoke test, no API calls
.venv/bin/python -m bottle_detector --source assets/test.mp4 --max-bottles 3        # limited AI run
.venv/bin/python -m bottle_detector                                                 # camera 0, full run
.venv/bin/python -m bottle_detector --help                                          # see all tuning flags
```

Run the GUI:
```bash
.venv/bin/python run_gui.py
```

Convert an existing detections JSON to an Excel report:
```bash
.venv/bin/python json_to_excel.py
```

Tests (pytest, configured via `pyproject.toml` `testpaths = ["tests"]`):
```bash
.venv/bin/python -m pytest
.venv/bin/python -m pytest tests/test_models.py
.venv/bin/python -m pytest tests/test_models.py::test_normalize_detection_payload_fills_arabic_labels
```

Build the Windows EXE (must run on Windows, uses a separate `.venv-win`):
```bat
build_windows.bat
```
Output: `dist\BottleDefectDetector\BottleDefectDetector.exe`. Note: if a `.env` exists in the project root when this script runs, it is copied automatically into the dist folder — anyone receiving that folder gets the embedded API key, so only hand it to trusted operators.

## Configuration

The Anthropic key/model are read from `.env` (see `.env.example`), supporting both `anthropic_api_key` and `ANTHROPIC_API_KEY`; model defaults to `ANTHROPIC_MODEL` or `claude-sonnet-5` (`bottle_detector/config.py`). `.env` is loaded twice in `AppConfig.__post_init__`: once resolved relative to the app base dir (`paths.resolve_app_path`, which uses `sys.executable`'s directory when frozen by PyInstaller, else cwd) and once via default `load_dotenv()` — this dual load is what lets the same code find `.env` both in dev and next to the frozen EXE.

## Architecture

Pipeline, wired together in `bottle_detector/runner.py::run_detector`, which both the CLI (`__main__.py`) and GUI (`run_gui.py`) call into:

1. **Frame source** (`cameras.py`) — opens a camera index (platform-specific backend: `CAP_DSHOW` on Windows, `CAP_V4L2` on Linux) or a video file via plain `cv2.VideoCapture`.
2. **Detection** (`tracking.py::BottleDetector`) — per-frame HSV color thresholding to find white blobs against the blue conveyor belt, locating the belt line first (`find_blue_belt_top`) then projecting each bottle's full extent — base through the screw-thread neck/opening, not just the cylindrical body — via `project_bottle_bases`. This line's bottles have a threaded neck above the body (no cap is ever screwed on, but the neck itself is a real part of the bottle and can be warped/torn — a `factory_defect`/`body_defect` case the pipeline must see). `project_bottle_bases` finds x-intervals from a narrow band straddling the belt line (the one place a reliable gap shows up even between touching bottles), then for each interval takes connected components of the white mask in a tall, capped search window and keeps the component that overlaps that belt band (anchoring to the same proven-reliable band, not an arbitrary fraction of the window, is what makes this robust — an earlier version used a fixed-fraction "reaches near the bottom" cutoff and it silently dropped most detections on lower-res footage by a few pixels' margin) — this is what lets the crop capture the true top of the bottle instead of stopping partway up the body. A morphological closing pass on the mask before labeling bridges the thin white bridge between neck and shoulder that motion blur/compression noise can otherwise break in isolated frames; without it, the neck flickered in and out of the detected component frame-to-frame, fragmenting tracking into many bogus duplicate captures of the same physical bottle (verified by comparing bboxes across consecutive frames on real footage — one specific instance went from 15 genuine bottles to 36 spurious captures before this fix). `_looks_like_bottle`'s aspect-ratio sanity check (`0.30 <= w/h <= 1.05`) is what catches the other over-counting case this pipeline has actually hit on real footage: a bottle that has fallen over and is lying on its side reads much wider than any standing bottle (1.46-1.50 observed vs. ~0.9 max for a real standing one, even in a crop spanning multiple bottles) — the bound used to sit at 1.45, just above that, letting it through and producing both a nonsense crop (the fallen bottle plus whatever stands behind it) and duplicate captures a few frames apart as the unstable box confused tracking. A fallen bottle isn't in an inspectable orientation anyway, so this bound intentionally rejects it outright rather than trying to detect it correctly. Separately, real conveyor footage can still produce one further failure mode this doesn't cover: multiple bottles packed with literally zero visible gap between them in a given frame merge into a single detection (confirmed on real footage, `IMG_9792` — 3 bottles fused into one crop) since the belt-line gap the x-interval logic depends on genuinely isn't there to find; this is a rare (~1/114 in the observed data), hard-to-fix-in-software edge case tied to how tightly bottles happened to be spaced at that moment, not a code bug with an obvious fix. Pure geometry/color heuristics, no ML model for detection itself.
3. **Tracking** (`tracking.py::BottleTracker`) — greedy nearest-centroid + IoU matching frame-to-frame to keep a stable `Track` per physical bottle; a track becomes a "capture candidate" once it's been seen a few frames and its centroid sits inside the configured `capture_start`/`capture_end` horizontal zone (avoids capturing bottles still entering/exiting frame).
4. **Async AI analysis** (`ai.py`) — each captured bottle crop is submitted to a single-worker `ThreadPoolExecutor` calling one of three interchangeable `AnalyzerProtocol` implementations: `NoAiAnalyzer` under `--no-ai`, `AnthropicBottleAnalyzer` normally, or `YoloThenClaudeAnalyzer` under `--use-yolo-prefilter` (selected in `runner.py::run_detector`) — so frame reading isn't blocked waiting on the API. Results are collected non-blockingly each loop iteration (`collect_finished`) and drained at the end (`wait_for_pending`). Analyzer failures are caught per-crop and turned into a synthetic "couldn't analyze" defect rather than aborting the run — a bad API call never kills the conveyor loop. Since the Anthropic API has no fine-tuning/persistent memory across calls, `AnthropicBottleAnalyzer.__init__` loads a small set of few-shot reference photos once (via `build_reference_content_blocks`, from `assets/reference_bottles/`) and prepends them to every single analysis call's message content, so the model has a real visual anchor for this bottle model's actual defects instead of judging from the text prompt alone. `REFERENCE_DEFECT_GROUPS` in `ai.py` maps each defect type to its own list of reference filenames + description text (`dent_defect_1/2.jpg` and `body_defect.jpg` for `body_defect`, `dirty_1-4.jpg` for `dirty`, `factorial_damage.jpg` for `factory_defect`) — any supported image extension (`.jpg`/`.jpeg`/`.png`, resolved via `find_reference_file`) present under those exact base names is picked up automatically, no code changes needed, missing files are silently skipped. The prompt draws a deliberate severity line between `body_defect` (moderate, localized: dents, scratches, a warped neck-opening ring) and `factory_defect` (large, gross, unmistakable structural malformation, e.g. a big lump of excess plastic) — this distinction was verified to hold under real API calls (the neck-warp example stays `body_defect` even with `factory_defect` available as a competing category). If detection is inconsistent on a particular defect look, the fix is almost always to swap in a clearer/more representative example image under `assets/reference_bottles/`, not to tweak the prompt further — this is exactly how the `body_defect` under-detection bug (bottles with a visible dent inconsistently marked "OK") got fixed. `build_windows.bat` copies this whole folder beside the packaged EXE the same way it copies `.env`, since `paths.resolve_app_path` resolves it relative to the frozen exe's own directory, not PyInstaller's bundle.
5. **Validation/normalization** (`models.py`) — Claude is asked to return minimal compact JSON (`defects[].type/description_ar`, `summary_ar`, `confidence`, no markdown) to keep output tokens low; `label_ar` is never requested from the model — it's always filled in locally from the fixed `LABELS_AR` map. `normalize_detection_payload` maps loose/aliased defect-type strings (e.g. "scratch", "stain", "molding") onto the three canonical `DefectType`s (`body_defect`, `dirty`, `factory_defect` — this conveyor line manufactures bottles without caps, so there is no cap-defect category) and clamps `confidence` into `[0, 1]`. Pydantic models enforce non-empty Arabic text via validators.
6. **Output** (`exporter.py`, `json_to_excel.py`) — detections are sorted by sequence and written as JSON; `write_run_output` also computes a run-level `RunStatistics` block via `compute_run_statistics`. `run_detector` then always calls `export_excel_report` to produce a timestamped `result/detections_TIMESTAMP.xlsx` plus `result/detections_latest.xlsx` (skipped/best-effort if that file is currently open/locked). The Excel workbook opens on a combined Arabic summary+details sheet, with `Summary` and `Bottle Details` as separate sheets. The `Report` and `Bottle Details` sheets both embed a resized JPEG thumbnail of each bottle's crop (via `write_bottle_rows`/`build_thumbnail` in `json_to_excel.py`) in the last column, anchored to that bottle's row with a matching row height; `resolve_crop_path` handles both absolute `crop_path` values (the normal case from a live run) and relative ones (e.g. hand-edited/legacy JSON) by trying them against cwd and against the input JSON's grandparent directory.

### Accuracy/Precision/Recall are confidence proxies, not real ML metrics

There is no manual ground-truth inspection step in this pipeline, so `accuracy_pct`/`precision_pct`/`recall_pct` are **not** statistically rigorous — they're derived entirely from the AI's own self-reported `confidence` (0-1) for its verdict on a bottle, both per-detection (`DetectionResult` computed fields in `models.py`) and aggregated per-run (`RunStatistics`/`compute_run_statistics`):
- `accuracy_pct` = confidence in the overall verdict — set for every bottle/run.
- `precision_pct` = confidence restricted to bottles where a defect *was* flagged — `None` when nothing was flagged.
- `recall_pct` = confidence restricted to bottles verdict-clean (no defects) — `None` when the bottle was flagged defective.
Per bottle, exactly one of `precision_pct`/`recall_pct` is populated (mutually exclusive by definition above) while `accuracy_pct` always is. If real precision/recall against ground truth is ever needed, it requires adding a manual-inspection input to compare against — there's no way to derive it from AI confidence alone.

### Optional YOLO pre-filter (`--use-yolo-prefilter`) — architecture built, prototype model trained on real video data

`bottle_detector/yolo_classifier.py::YoloCleanClassifier` wraps a two-class YOLOv8 classification model (`clean`/`defective`) meant to screen out confidently-clean bottles before they reach Claude, cutting API cost/latency on a real production line. `ai.py::YoloThenClaudeAnalyzer` composes it with a normal `AnthropicBottleAnalyzer`: YOLO runs first, and only forwards to Claude when its top prediction isn't `clean` or its confidence is below `AppConfig.yolo_clean_confidence_threshold` (default `0.90`) — deliberately conservative, since a missed defect is worse than an extra Claude call. `DetectionResult.analysis_stage` (`"yolo"` or `"claude"`) records which stage produced each verdict, both for transparency and because it's a natural signal for prioritizing which bottles need human review when building the training set later.

`YoloCleanClassifier.__init__` checks for the model file (`AppConfig.resolved_yolo_model_path`, default `models/yolo_bottle_classifier.pt`) before importing `ultralytics` at all, and raises `RuntimeError` immediately if it's missing — by explicit design this does *not* silently fall back to Claude-for-everything, since the flag is opt-in and only meant to be turned on once a model actually exists (see `models/README.md`).

#### `scripts/prepare_yolo_dataset.py` + `scripts/train_yolo_classifier.py`

`prepare_yolo_dataset.py` builds `training_data/{train,val}/{clean,defective}/` from two label sources: `assets/reference_bottles/` (the few-shot images, `clean_ok.jpg` = clean, everything else = defective) and `outputs/crops/` + `outputs/detections.json` (real run crops, labeled by whether Claude flagged any defect). If `detections.json` wasn't produced by a real Claude run (`model == "no-ai"`, e.g. a smoke test), it falls back to the hand-verified `scripts/manual_crop_labels.json`. It uses two independent `random.Random` instances — one for the train/val split, one for augmentation — deliberately kept separate so changing augmentation logic can never silently perturb which images get held out for validation (they shared one RNG originally; that coupling was a real bug, fixed once discovered). It generates augmented variants of every training image, each a random mix of flip/rotation/perspective-warp/brightness/contrast/color/sharpness jitter/zoom/Gaussian-blur/Gaussian-noise/random-erasing (Pillow + numpy). Because the two classes have different amounts of real source data, `build_dataset()` boosts the augmentation count for whichever class has fewer real photos (`AUGMENTED_VARIANTS_PER_IMAGE=20` baseline, up to `MAX_AUGMENTED_VARIANTS_PER_IMAGE=60`) so both classes end up with a comparable number of final training images instead of the majority class dominating what the model learns — this is a real fix for a real class-imbalance problem (86 clean vs. 56 defective base images produced a lopsided ~2400 vs. ~300 training set before this was added). `train_yolo_classifier.py` trains *both* `yolov8n-cls` and `yolov8s-cls` with dropout/label-smoothing/weight-decay regularization and extra live augmentation (`degrees`/`translate`/`scale`/`shear`/`hsv_*`/`erasing` train() kwargs), evaluates both on the held-out val split, and keeps whichever scores higher (nano wins ties — faster/lighter for a real-time pre-filter, and a small val split can't meaningfully separate close scores anyway) as `models/yolo_bottle_classifier.pt`.

**Labeling standard is zero-tolerance**: `scripts/manual_crop_labels.json` labels a bottle `defective` if it has *any* visible mark at all, no matter how small — a single 1-3px speck is enough. A bottle is only `clean` if its surface is pure, unbroken white with nothing visible on it. An earlier labeling pass treated faint sub-pixel-scale specks as camera/compression noise and left them `clean`; that was a real mistake caught during review (a specific held-out crop with a small visible mark was being scored "clean" when it should not have been) and the entire label set was re-audited crop-by-crop against the strict standard, moving 38 previously-"clean" crops to `defective`. Any future manual labeling pass on new crops must use this same strict standard, or the class balance and the model's real-world behavior will drift back toward under-flagging small defects.

**Current status is a prototype, not production-grade, but trained on real conveyor video now**: the training data is ~142 base labeled images (86 clean, 56 defective) — most of it 120 real bottle crops extracted from 6 conveyor videos in `videos/*.MOV` and individually visually inspected (not synthetic/staged photos), plus the original ~25 calibration-video/reference images. That's close to but still under the ~150-300+ per class generally needed for a real classifier. Held-out validation accuracy is 95% (up from 92.3% on an earlier, more class-skewed version of this dataset trained before the video data and stricter labeling standard were incorporated), though with only 20 held-out images (10 clean / 10 defective) that number is indicative, not statistically strong. Both scripts are designed to be re-run with zero code changes as more real, Claude-labeled crops accumulate in `outputs/` from actual production use — that's the intended path to a production-grade model.

Note: `torch`/`torchvision` must come from matching builds (both `+cpu` or both CUDA) — installing plain `pip install torch torchvision` can silently mix a `+cpu` torch with a non-`+cpu` torchvision wheel and fail at import time with `RuntimeError: operator torchvision::nms does not exist`. If hit, reinstall both from the same index, e.g. `pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu`.

Cross-cutting concerns:
- `progress_callback`/`preview_callback` in `run_detector` are how the GUI observes detector state (status text, live frame preview) without the runner knowing about Qt; the CLI just doesn't pass them and instead uses `--no-display`/OpenCV's own window.
- `stop_event` (a `threading.Event`) is the cooperative-cancellation mechanism — GUI's stop button and CLI's `q` keypress both feed into it, and on stop the runner still waits for in-flight AI analyses before writing final output.
- `paths.resolve_app_path` is the one place that needs to know about PyInstaller's frozen-exe layout; anything reading/writing files relative to the app root should go through it rather than assuming cwd.

### Production-hardening pass

A few reliability gaps were closed once the geometry/detection issues above were fixed and stable:

- **Live-camera read resilience** (`runner.py`'s main loop): a single failed `capture.read()` used to end the entire run immediately, which is correct for a video file (EOF) but wrong for a live camera, where a transient USB/driver hiccup can cause one bad read without the feed actually being gone. For a live camera source (`isinstance(parsed_source, int)`), the loop now retries up to `CAMERA_READ_MAX_CONSECUTIVE_FAILURES` (30, a few seconds at typical frame rates) with a short delay before giving up; a video file still stops immediately on the first failed read, since that's a real EOF.
- **Structured logging** (`bottle_detector/log_config.py`): `print()` calls in the core pipeline (`runner.py`, `ai.py`) were replaced with a proper `logging` setup — console output plus a rotating file (`logs/bottle_detector.log`, 5MB × 5 backups, resolved via `paths.resolve_app_path` so it lands next to the frozen EXE too). This matters most for the packaged GUI/EXE case: nobody is watching a terminal on an actual production line, so the log file is what makes a failed or oddly-behaving run diagnosable after the fact. `get_logger(__name__)` lazily calls `configure_logging()` on first use, so importing any module that uses it is enough to wire logging up — no separate init call needed anywhere.
- **Claude API resilience**: the `anthropic` SDK already retries transient errors (connection issues, timeouts, 429/5xx) on its own with backoff (`max_retries=2` by default) — `AnthropicBottleAnalyzer` now constructs the client with `max_retries=5, timeout=60.0`, since a bottle that exhausts retries becomes a permanent "couldn't analyze" placeholder (see `ai.py`'s except block), so it's worth spending extra seconds riding out a flaky connection rather than giving up early. A failed analysis is now also logged (`logger.error`, includes the bottle sequence/frame and the exception) instead of only being visible in the output JSON.
- **Regression tests for `tracking.py`** (`tests/test_tracking.py`): this module was the single most bug-prone part of the whole project (rounded-base width under-measurement, touching-bottle merging, neck-crop truncation, neck/shoulder connectivity flicker fragmenting tracking into duplicate captures, fallen-bottle detection) — all found and fixed through manual, ad hoc debugging against real video. 20 tests now lock in that history using synthetic masks (no real video files needed, so they're fast and deterministic in CI): belt-line detection, column-interval merging, full neck-to-base height recovery, touching-bottle splitting (with the measured real-gap threshold the closing-kernel tradeoff imposes — see the comment above the closing kernel in `project_bottle_bases`), neck/body gap bridging, fallen-bottle aspect rejection, and basic tracker capture-eligibility. Run with `.venv/bin/python -m pytest tests/test_tracking.py -v`.

**What this does *not* claim to fix:** these changes make the pipeline more robust to real operational conditions (camera hiccups, transient network issues, silent failures) and protect the hard-won detection-geometry fixes from regressing. They do **not** change the YOLO pre-filter's fundamental data-volume limitation (still ~135 base images, see the YOLO section above) — that only improves as more real, Claude-labeled crops accumulate from actual production use, which is not something more code can produce. Nor do they guarantee correct behavior under camera/lighting/mounting conditions meaningfully different from the 6 videos this was debugged against; treat any new camera setup as needing its own round of verification before trusting it unsupervised, the same way the original 4K footage in this project surfaced bugs the old calibration video never did.
